00前言 · 矩阵为什么难懂

大多数教材讲矩阵旋转，一上来就是"把整个空间的网格抓住揉捏"——所有点同时变形、网格跟着弯折。这个模型在数学上是对的，但它要求你同时盯住无穷多个点，脑子里要渲染一整张会变形的网。对大多数人来说，这个认知负载太高了，于是矩阵就变成了"一坨会算出正确答案但不知道在干嘛的数字"。

这一页换一个极简模型，只盯住两样东西：

➡️
一支箭头
一根从原点出发、初始指向 x 正方向、长度为 1 的箭头。它代表"x 轴转到了哪里"。旋转矩阵里所有的数字，都是这支箭头（和它垂直的伙伴）的尖端坐标。
🔴
一个点
空间里任取一个点 P。它的坐标 (x, y) 不是"位置编号"，而是混合两支箭头的配方比例：x 份 x 箭头 + y 份 y 箭头，就调出这个点。矩阵变换点 = 换一套箭头，按原配方重新调。

先别急着理解上面每一句话——这一整页就是围绕这两句话展开的。读完第一章你会知道：

  • 旋转矩阵的每个数字是从哪来的：不是背出来的，是箭头尖端的读数抄进表格；
  • 矩阵乘向量在算什么：按坐标比例混合新箭头，调出新位置；
  • 空间（本地/世界/摄像机/屏幕……）是什么：一个点（原点）加一组箭头（基）而已——和第一章的模型完全同构；
  • 空间转换在做什么：不是搬运物体，是"同一个事实，换一套读数"；
  • 嵌套链（本地→摄像机→世界……任意顺序）怎么算：一站一站换读数，矩阵从右往左依次生效。
预备知识：只需要初中代数，外加三角函数里 cos / sin 的最朴素含义——在直角三角形里，cosθ = 邻边/斜边、sinθ = 对边/斜边。长度为 1 的箭头转 θ 角后，尖端水平读数就是 cosθ、竖直读数就是 sinθ。忘了也没关系，下一节现场复习。
矩阵不是一个数字表格。它是一份登记表：登记"原来的箭头，现在住在哪里"。

01第一章 · 一支箭头讲清旋转矩阵

本章只回答一个问题：旋转矩阵 [[cosθ, −sinθ], [sinθ, cosθ]] 里的四个数，凭什么长这样？答案只需要一支箭头。

1.1 一支箭头：尖端落点就是答案

拿一支长度恰好为 1 的箭头，尾巴钉在原点，箭尖指向 x 正方向。现在让它绕原点逆时针转 θ 角。问：箭头尖部落在哪里？

画一面墙（竖直线）和一块地板（水平线），从箭头尖端向它们做垂线，就得到一个直角三角形：斜边是箭头本身（长度 1），与水平方向的夹角是 θ。于是——

箭头尖端的读数（三角函数复习） 水平读数 = 1 × cosθ　　竖直读数 = 1 × sinθ

也就是说，这支箭头转到哪，它的尖端坐标就是 (cosθ, sinθ)。转 90°，尖端在 (0, 1)；转 180°，在 (−1, 0)。不需要任何矩阵知识，一支箭头加上 cos/sin 的定义，答案就出来了。

下面把这个过程做成演示。拖动角度滑块（或点"自动旋转"），盯着右侧矩阵表格的第一列——你会发现矩阵第一列的上下两个数，永远和画面里橙色箭头的尖端读数一字不差：

演示 1 · 箭头旋转器 —— 矩阵第一列 = 橙色箭头的尖端
灰色网格固定不动。橙色箭头就是本节的"那支箭头"（初始沿 +x，长度 1）；勾选后出现的绿色箭头是它垂直的伙伴（初始沿 +y）。右侧 2×2 表格就是旋转矩阵——第一列涂成橙色、第二列涂成绿色。转动滑块，看着箭头尖端的读数被"抄写"进矩阵对应列。

本节结论
旋转矩阵的第一列，就是初始沿 +x 的那支单位箭头旋转后的尖端坐标 (cosθ, sinθ)。矩阵不是发明出来的公式，是箭头尖端读数的登记表。
随堂小测 1
把箭头逆时针转 60°，矩阵第一列的上下两个数分别是？
尖端水平读数 = cosθ、竖直读数 = sinθ，所以第一列从上到下是 (cos60°, sin60°) = (0.5, 0.866)。回到演示里把 θ 拖到 60° 验证一下。

1.2 第二支箭头：凑齐矩阵两列

只有一支箭头还定不了一个坐标系——就像只有"东"没有"北"，说不清东南偏北多少度。所以我们再钉一支和橙色箭头垂直、同长、初始沿 +y 方向的绿色箭头。关键规则只有一条：

旋转的守规矩条款

两支箭头像焊在一起的直角尺：转多少一起转，始终保持垂直、长度不变。橙色转 θ，绿色也转 θ。所以在演示 1 里你只拖一个滑块，两支箭头却同步旋转——它们是同一把尺子的两条边。

初始沿 +y 的绿色箭头转 θ 之后，尖端落在哪里？三角函数再算一次，答案是 (−sinθ, cosθ)。可以拿两个特殊角验证：θ=90° 时它转到 (−1, 0)（指向 −x，正确）；θ=180° 时转到 (0, −1)（指向 −y，正确）。

现在把两支箭头的"新住址"并排抄进表格——第一列抄橙色箭头，第二列抄绿色箭头：

cosθ−sinθ
sinθcosθ
这就是著名的旋转矩阵——现在它是"抄"出来的，不是"背"出来的
读法总结：看到任何 2×2 矩阵，别急着算。先问：第一列是哪支箭头的新家？第二列呢？列里的数字是箭头尖端的读数。这个读法对剪切、缩放、镜像统统成立——比如"沿 x 拉伸 2 倍"就是把橙色箭头加长到 2（第一列变 (2, 0)），绿色箭头不动（第二列 (0, 1)）。旋转只是"两支箭头一起转圈"这种最常见的情况。

3D 完全同理：三维再钉一支垂直于前两支的 z 箭头，旋转矩阵 3×3 的每一列，还是对应箭头旋转后的尖端读数。下一章就把第三支箭头补齐，并升级成真 3D 演示。降维打击完毕——从现在起，"矩阵的列 = 箭头的新家"这条规则通吃到 4×4。

1.3 点的配方：坐标 = 混合箭头的比例

矩阵的列搞定了，还剩最后一个问题：拿矩阵去乘一个点，到底在算什么？

回到"配方"的视角。点 P 的坐标 (x, y) 的真正含义是：

坐标的配方读法 P = x × x̂ + y × ŷ　（x 份橙箭头，掺 y 份绿箭头）

比如 P = (2, 1)：从原点出发，沿橙色箭头走 2 步，再沿绿色箭头走 1 步，落点就是 P。这就是"坐标"的全部秘密——它不是编号，是配方。

那么旋转一个点 = 什么？配方不动，换原料。两支箭头转走了，但 P 依然按老配方"x 份新橙箭头 + y 份新绿箭头"重新调出来。调出来的位置，就是矩阵乘向量的结果：

矩阵乘向量 = 按老配方混合新箭头 M · P = x × M第1列 + y × M第2列

展开成数字，就是你熟悉的旋转公式（对照着读：x′ 的第一项是 x·cosθ，第二项是 y·(−sinθ)——每项都是"一份坐标 × 一支箭头的某个读数"）：

数值展开（第二章结束前你都不需要"记"它，看演示抄就行） x′ = x·cosθ − y·sinθ
y′ = x·sinθ + y·cosθ
演示 2 · 点的配方 —— 平行四边形调合法 + 数值逐步推演

第一章合体
矩阵的列 = 箭头的新家；坐标 = 配方；矩阵乘向量 = 按老配方混合新箭头。旋转矩阵里没有一个数字需要背——全是箭头尖端的抄写。

箭头讲完了方向，还差一个没讲的东西：家在哪。

02第二章 · 第三支箭头与原点：走进 3D

旋转绕着原点转，原点永远不动。但游戏里的物体要搬家——只动箭头还不够，得连"点"（原点）一起动。本章把模型补全成完整的两件套：箭头管方向，点管位置，并补上第三支箭头，正式进入三维。

2.1 平移为什么塞不进 2×2

试一试用 2×2 矩阵把所有点向右移 1：你需要 x′ = x + 1。但 2×2 矩阵乘向量只能做"坐标 × 箭头读数的加权混合"——每个输出都是 x、y 的乘积组合，变不出"+1"这种凭空多出来的常数。用箭头语言说：2×2 只登记了两支箭头，可平移挪的是原点本身，箭头一寸没动——表格里根本没有原点的房间。

解决方法直白得可爱：给原点也发一个登记栏。给矩阵加一行一列，第三列专门登记"新原点搬到了哪"：

cosθ−sinθtx
sinθcosθty
001
3×3 齐次矩阵：橙色列=x 箭头新家，绿色列=y 箭头新家，蓝色列=原点新家（最后一行 0,0,1 是固定脚手架）
打个比方：2×2 矩阵像一份"指南针校准单"（只改东南西北指向哪里），3×3 齐次矩阵是一份"搬家通知单"：前两列写新指南针指向，第三列写新门牌地址。旋转缩放是"原地转向"，平移是"换门牌"，两件事写在同一张 3×3 单子上。

2.2 第三支箭头与 4×4 统一布局

三维空间需要三支互相垂直的单位箭头：x̂、ŷ、ẑ。其中任何一支的"新家"，仍然抄进矩阵对应的一列。以"绕 z 轴转 θ"为例——x̂ 和 ŷ 像第一章那样转圈，ẑ 站在转轴上原地不动：

cosθ−sinθ0
sinθcosθ0
001
绕 z 旋转 Rz(θ)：第三列 = (0,0,1) —— z 箭头没动，它的新家就是老家

绕 x 转（Rx）就是换成 ŷ、ẑ 互相追赶着转圈、x̂ 站轴上不动；绕 y 同理。所以 3D 的任意旋转 = 三支箭头各自的新家，依然是"抄箭头尖端"，一条规则都没加。最后把原点栏也补上，得到游戏引擎里无处不在的 4×4 矩阵：

矩阵布局总纲（背这一句就够了）

矩阵 = [ 箭头₁ | 箭头₂ | 箭头₃ | 原点 ]

前三列（橙/绿/青）= 三支箭头的新家；第四列（蓝）= 原点的新家。2D 的 3×3 是它的缩水版。

最后一行 w（恒 0,0,0,1）是干嘛的：齐次坐标的"脚手架"，永远不用动——前三个 0 挡住平移反向污染箭头（箭头是纯方向，搬家不该改变朝向）；最后的 1 让第四分量 w=1 的点能"接住"第 4 列的平移。由此区分两种东西：位置 w=1（会被搬家），纯方向 w=0（平移对它无效——法线、朝向就是方向）。透视投影会故意改写这一行，除以 w 就得到近大远小（5.2 节）。
读实时矩阵的两个新指示（本页所有演示已启用，与《盒子的矩阵课》《实验室》同款）：① 表格顶部的彩色列头与左侧行标——竖着读一列 = 一支箭头的新家；② 带下划线加亮的格子 = 参与了变化（数值离开了单位矩阵）：没有变换时一个都不亮，转/拉/搬之后亮起的格数恰好等于参与该动作的格子数。

一个常见误解：别把"原点在最后一列"记成"最后一行"。本页全部采用列向量约定（矩阵左乘列向量，M·p）。有些 API（老式 DirectX 教材、某些引擎源码）用行向量 p·M，那时原点住在最后一行，整体书写互为转置——数学是同一套，详见第 6 章坑位表。
变换从来不是"把世界搬来搬去"，而是"同一个世界，换一把尺子重新读数"。

03第三章 · 空间 = 一个点 + 一组箭头

前两章攒齐了全部零件：原点（点）+ 基（三支箭头）。现在宣布一个定义：所谓"空间"（坐标系），就是一个点加一组箭头。所谓"空间变换"，就是拿着一套登记表，把同一件事实在两套登记表之间换算。

3.1 变换的两副面孔：移动 vs 换读数

这是全页最容易卡住、也最值得卡一下的地方。同一个矩阵，有两种完全等价的读法：

观点矩阵在干什么典型台词
主动观点 把点/物体在同一个坐标系里搬走：箭头转了，点按新配方调到新位置 "把这个角色旋转 30°" —— 角色真的动了
被动观点 坐标系换了，点原地不动，只是它的读数按新尺子重新报数 "转到角色本地空间看看" —— 世界没动，换读数

两副面孔为什么是同一个矩阵？因为"新箭头相对旧箭头转 +θ"和"旧读数相对新箭头转 −θ 报数"是同一份登记表——尺子顺时针拧 θ，读数就逆时针多出 θ。图形学日常里：渲染顶点用主动观点（顶点真的被搬到屏幕各处），空间转换用被动观点（位置是客观事实，本地读数/世界读数/摄像机读数是几套描述）。

打个比方：同一根电线杆，从村口牌坊量过去是 300 米，从学校门口量过去是 120 米。电线杆没动，动的是量法的起点和方向。"世界坐标 → 本地坐标"就是从"以村口为原点报数"换成"以学校门口为原点报数"。矩阵就是那张换算表。

3.3 逆变换：沿来路回去

从本地读数换到世界读数用登记表 M；从世界换回本地，就用逆表 M⁻¹。直觉：正着走"旋转 θ 再平移"，反着走就得"先平移回去，再旋转回去"——顺序整个倒过来，每一步取逆（像脱衣服：穿的时候先袜子后鞋，脱的时候先鞋后袜子）。

逆 = 倒序逐个取逆 (A·B)⁻¹ = B⁻¹ · A⁻¹

旋转矩阵有一个几乎免费的福利：它的逆 = 转置（把行列互换）。用箭头语言三秒看懂：三支箭头单位长且互相垂直，说明登记表的前三列是"标准好箭头"；这样的表转置之后，行也自动是"标准好箭头"，而好箭头表 × 好箭头表(转置) = 单位矩阵。引擎里这一条省掉无数求逆计算：

正交矩阵（纯旋转）的逆 R⁻¹ = Rᵀ　　（含平移时：R 部分转置，t 部分变为 −Rᵀt）
为什么演示 4 的逆表数字"长得像"原表：观察 M⁻¹ 的 3×3 部分，和 M 的 3×3 部分沿对角线互为镜像——那就是转置。只有原点列经过 −Rᵀt 的加工。这也解释了为什么法线变换常用"逆转置"：法线是"方向读数"，方向只用箭头部分描述（第 6 章还会再提一句）。
名字不同的空间，其实只是"原点和箭头钉在哪里"不同的几套登记表。

04第四章 · 引擎空间词典：本地 / 世界 / 实例 / 摄像机 / 屏幕

游戏引擎给几套常用的登记表起了名字。本章逐个认识它们，并给出"任意两个空间怎么互转"的通用方法。

4.1 引擎里的六个空间

  • 本地空间（Local / Object）建模时用的表：原点钉在物体自己身上（通常是轴心/骨架根），箭头沿物体朝向。美工做模型、动画师 K 帧，都在这张表里读数。它的好处是自带相对性：物体怎么跑怎么转，本地读数永远不变。
  • 父空间 / 层级（Parent / Hierarchy）有挂靠关系时中间会经过的表：角色的"手"挂在"手臂"上，手臂挂在"肩膀"上……每层一张表。第五章细讲嵌套。
  • 世界空间（World）整个场景公用的表：原点和箭头全局唯一、绝对静止（对场景而言）。逻辑层的大多数问题（"两物距离多远""谁在谁前面"）都在世界表里问，因为它对所有物体公平。
  • 实例空间（Instance）同一份本地数据被"复印"很多份时，每一份复印各自领一张表：实例化网格（ISMC/HISM）的每个实例、每个 Niagara 粒子、每株草地，都是"一套本地点+箭头"。数据只有一份，表有 N 张——这是实例化省内存的全部原理。
  • 摄像机/观察空间（Camera / View）原点钉在相机上、一支箭头沿视线方向的表。渲染前把所有东西的读数换到这张表里，"深度"就变成一个普通坐标，剔除和投影都变得好算。
  • 裁剪空间 → NDC → 屏幕空间（Clip / NDC / Screen）投影矩阵产出的表：三个坐标都压到 [-1,1]（NDC，Normalized Device Coordinates），最后一步"视口变换"把它摊成像素编号。屏幕空间里没有"米"，只有像素行列号——你屏幕上的每一个像素坐标，都是这张表的读数。
一句话记住它们：本地=自己的表，父=上级的表，世界=全场公用的表，实例=复印件各自的表，摄像机=镜头前的表，屏幕=像素编号表。每个名字回答的都只是同一个问题：原点和箭头钉在哪？

它们连成一条流水线

实例空间插一句：实例空间在流水线图里不在主链上——它其实是"若干张本地表"的别名。实例 i 的世界读数 = M(实例i) × 本地读数，一步到位。下一节专门玩它。

4.3 空间关系图与"任意两空间互转"

把 4.1 的流水线图当成一张地铁线路图：每个空间是一个站，每条边是一张登记表。要从任意一站到另一站，方法唯一：

🚇
任意两空间互转 = 沿图找一条路，把路上的表按"离起点近的在右"的顺序连乘
例：本地 → 摄像机 = V · M（先坐 M 从本地到世界，再坐 V 从世界到摄像机）。反着走就把每张表换成逆表、顺序倒过来：摄像机 → 本地 = M⁻¹ · V⁻¹。没有直达线路就多换几站，本质全是同一件事：一站一站换读数。
常用线路（列向量约定） 本地→世界：p_world = M · p_local
世界→本地：p_local = M⁻¹ · p_world
本地→摄像机：p_view = V · M · p_local　（路过世界，换乘）
摄像机→本地：p_local = M⁻¹ · V⁻¹ · p_view　（原路返回）
随堂小测 3
把本地系整体旋转 10°（物体本身没动），P 的"世界读数"会变吗？
被动观点：P 是客观事实，世界表没动，世界读数当然不变；变的是 P 相对新本地箭头的配方——本地读数变了。回演示 4 里转 yaw 滑块亲眼确认。
再长的链，也是一站一站换读数换过去的——每站只做一件小事。

05第五章 · 链式与嵌套：从子物体本地到屏幕像素（真 3D）

最后一块拼图：当空间一层套一层（子物体在父物体里、父在世界里、世界在镜头里），读数怎么一站一站传下去？乘法顺序为什么不能乱？本章的演示用真实透视投影一路算到像素。

5.1 乘法顺序：右边的先干活

矩阵乘向量是从右往左生效的——因为右边的矩阵离点最近：

渲染总公式（列向量约定） p_screen = Proj · V · M · p_local

读法：p_local 先被 M（本地→世界）换算，再被 V（世界→摄像机）换算，最后被 P（投影到屏幕）。就像流水线工位：原料从最右边的工位进，从最左边的工位出。

穿衣服定理：早上先穿袜子再穿鞋，写成式子是 鞋·袜·脚（右边的先套上）。晚上脱的顺序必然是 袜⁻¹·鞋⁻¹——整体倒序、每件取逆。矩阵链同理：正向 M·…，逆向就倒着剥。

顺序为什么不能乱？因为"先转再挪"和"先挪再转"结果不同：转完再挪，挪的是世界方向；先挪再转，那段平移会被旋转带着走，落点完全两回事。旋转+平移不满足交换律——只有"纯旋转乘纯旋转（同轴）"等少数组合才与顺序无关。下一节的演示里专门放了顺序对照实验。

5.2 全链路推演：子本地 → 父本地 → 世界 → 摄像机 → NDC → 屏幕像素

透视除法：全流水线唯一一次"除法"

投影矩阵把相机系读数变成"裁剪坐标"——xyz 各乘了不同系数，并顺手产出第四个分量 w = −z（离相机越远，w 越大）。下一步把 xyz 全部除以 w，得到 NDC：近处的点 w 小、除完数值大（被推离中心 → 显得大），远处的点 w 大、除完被拉向中心（显得小）。"近大远小"这四个字，物理上就是一次除法。最后视口变换把 [−1,1] 摊成像素行列号（y 翻转，因为像素行号向下数）。把 P 拖到视锥外面，第 5 站会显示"不在屏幕内"——裁剪就发生在这一步之前。

5.3 嵌套层级与逆向走链

嵌套（骨骼、Actor 挂 Actor、UI 套 UI）没有新数学，只有一条站位规则：

🪆
离点最近的表，写在最右边
p_world = M(父) · M(子) · M(孙) · p_孙本地。链条从点身边开始向外生长，一层层向外换乘。反求本地读数则整体倒序取逆：p_孙本地 = M(孙)⁻¹ · M(子)⁻¹ · M(父)⁻¹ · p_world。

为什么要嵌套而不是直接给每个物体发一张"本地→世界"表？因为局部性：手臂一抬，手、手指、指甲上全部顶点的"相对手臂"读数一个都不用改，只有手臂那张表变了——链条自动把影响传下去。要是每个物体都直存世界表，抬一次手臂要重算所有子孙的表。动画骨骼、挂件系统、层级 UI，全是这条局部性的红利。

随堂小测 4
p_screen = P·V·M·p_local 中，第一个生效的矩阵是？
矩阵链从右往左作用：最右边的 M 离 p_local 最近，先把它从本地读数换成世界读数；P 写在最左，最后才生效。"右边的先干活。"

06第六章 · 常见坑与引擎事实

坑 / 事实一句话拆解
乘法顺序反了右边的先作用。调试时把链拆开逐站代入，看读数在哪一站开始不对——比盯最终错误结果高效得多。
行向量 vs 列向量数学/GLSL 常用 M·p（列向量，原点在最后一列）；老式 DirectX 教材用 p·M（行向量，原点在最后一行）。同一变换两种书写互为转置。读引擎源码先看它用哪种约定。
左手系 / 右手系同样的"绕 z 转 +90°"，左右手系转出的方向相反（判据：用哪只手的四指从 x 卷向 y，拇指即 z）。跨引擎/跨 API 移植时先确认手性，再谈数值。本页 3D 演示 = 右手系（x 前、y 左、z 上）；UE = 左手系（x 前、y 右、z 上）——只差 y 箭头朝向。
NDC 的 z 范围OpenGL 惯例 z∈[−1,1]，Direct3D 惯例 z∈[0,1]，Vulkan 还要翻转 y。写跨 API shader 时深度范围不能想当然。
引擎存四元数不存矩阵UE 的 FTransform = 四元数(旋转) + 平移 + 缩放：省内存（4 个数 vs 9/16 个）、可球面插值、无万向节锁。要用的时候才组装成矩阵——组装顺序：先缩放、再旋转、后平移（即 T·R·S）。
法线要用"逆转置"法线是方向读数（只用箭头部分）。物体带非均匀缩放时，直接用同一个 M 变法线会把垂直关系拉歪，要用 (M⁻¹)ᵀ 的 3×3 部分——这是 3.3 节"逆=转置"在工程里最常见的露面。
本页全部数值都可复算：六个演示的每个读数（包括 3D 投影与像素坐标）都是现场计算的真实数值（非预设动画）。如果你在任何一本教材/引擎文档里看到的数字与本页演示不一致——先怀疑约定（行/列向量、手性、角度方向），再怀疑公式。

模型

  • 箭头：单位长、互垂直；矩阵的列 = 箭头旋转后的尖端读数
  • 点（原点）：矩阵的最后一列；平移只改它
  • 坐标 = 配方：P = x·x̂ + y·ŷ (+ z·ẑ)；矩阵乘向量 = 按老配方混合新箭头
  • 空间 = 点 + 三支箭头；空间变换 = 换表重报读数（被动观点）

公式

全部公式一屏 R(θ) 的列 = 各支箭头旋转后的尖端读数
M·P = x·列₁ + y·列₂ (+ z·列₃)
齐次布局 = [ 箭头 | 箭头 | (箭头 | 箭头) | 原点 ]（3D 为 4×4）
(A·B)⁻¹ = B⁻¹·A⁻¹　　R⁻¹ = Rᵀ（纯旋转）
p_world = M父·M子·p_子本地　（离点最近的在右）
p_clip = P·V·M·p_local → /w → NDC → 像素
